# Sprint 1: Operational Support Log Analyzer

## The Support Team Situation
The internal operations support team is currently experiencing significant operational strain due to the manual overhead of daily log triage. Every morning, multiple backend applications dump massive text logs—ranging from a few dozen lines to upwards of 200,000 lines—into a shared directory. An engineer must manually open these raw text files in Windows Notepad and scroll line-by-line using the mouse wheel to visually spot critical failures. Because over 99% of the log volume consists of healthy system tracking messages, this workflow causes extreme eye strain, introduces high latency in detecting system out-of-memory errors or database timeouts, and creates an environment where severe production defects are easily missed during high-volume periods.

## System Solution
This utility provides an automated, terminal-based solution designed to instantly eliminate manual scrolling and isolate system failures for immediate triage. Built entirely within the structural constraints of the Python standard library to ensure zero environment setup, the tool establishes a memory-safe stream that reads log data sequentially one line at a time. It parses each text row according to a strict three-split token rule, automatically verifying structure and filtering out successful transactional telemetry. The system isolates actionable severity keywords at a specific position to prevent false-positive matching inside log message bodies. It then compresses identical errors into a deduplicated internal catalog, outputting a high-level summary report directly to the command line sorted by frequency so engineers instantly see the most critical and recurring problems first.

## Scope Boundaries & Limitations
To meet strict timeline targets and keep the runtime lightweight, several distinct design choices were deliberately pushed out of scope for this initial sprint. The tool explicitly operates on a stateless per-line basis; it processes one log file at a time and treats each line as an independent string segment, meaning multi-line stack trace grouping and folder-wide directory scanning are non-goals. Furthermore, custom query filtering by specific timestamps or service components has been left out to avoid unnecessary scope creep. Finally, because the tool tracks uniqueness via a direct string match on the raw log message, any errors containing dynamic runtime data—such as shifting user IDs, port numbers, or variable timestamps embedded inside the message payload—will register as separate unique entries with individual counts of one.
